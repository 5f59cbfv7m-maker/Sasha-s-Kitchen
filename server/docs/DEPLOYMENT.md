# Развёртывание и железо

Вы сказали, что железо подберёте под результат и ограничений нет. Ниже —
конкретные рекомендации, а не «зависит от нагрузки»: что взять сейчас, что
поменять на первом росте и где будет больно.

## Коротко

**Возьмите обычный Linux-хостинг с выделенными ресурсами (VPS/bare metal),
а не managed-платформу.** Причины две: магазину нужен PostgreSQL с
расширениями (`pg_trgm`, `btree_gin`) и собственными индексами, и нужен
объектный сторидж под видео. На managed-PaaS и то и другое упирается в
чужие лимиты и стоит кратно дороже.

PostgreSQL — да, на Linux, как вы и предположили. Это правильный выбор:
вся модель данных построена на его массивах, полнотекстовом поиске и
частичных индексах. Переносить это на другую СУБД смысла нет.

## Топология

```
        клиенты (iOS, позже Android/Windows)
                 │
              [ CDN ]  ← отдаёт всё видео и фото
                 │
           [ nginx / caddy ]  ← TLS, лимиты, статика
                 │
          [ api × 2+ ]   ← Go, stateless, любое число реплик
             │      │
     [ PostgreSQL ] [ Redis ]
             │
      [ worker × 1+ ]  ← транскодирование видео (ffmpeg)
             │
     [ S3-совместимый сторидж ]  ← MinIO свой или облачный S3
```

`api` не хранит состояние: масштабируется горизонтально простым
добавлением реплик. `worker` — отдельный процесс, потому что
транскодирование съедает CPU и не должно конкурировать с обработкой
запросов.

## Железо на старте

Для запуска и первых тысяч пользователей:

| Узел | Ресурсы | Зачем именно столько |
|---|---|---|
| API | 2 vCPU, 4 ГБ | Go отдаёт JSON почти бесплатно; упрётся в БД раньше, чем в себя |
| PostgreSQL | 4 vCPU, 16 ГБ, **NVMe SSD** | ОЗУ важнее ядер: рабочий набор должен помещаться в кэш |
| Redis | 1 vCPU, 2 ГБ | Кэш витрины, не хранилище |
| Worker | 4 vCPU, 8 ГБ | ffmpeg упирается в CPU; каждое видео — минуты работы |
| Сторидж | от 500 ГБ, расширяемо | Видео растёт быстрее всего |

Всё это спокойно живёт на **одной машине 8 vCPU / 32 ГБ / 1 ТБ NVMe** на
старте. Разносить по отдельным узлам стоит тогда, когда начнёт мешать
соседство, а не заранее.

**NVMe обязателен, не SATA.** Это единственная позиция, на которой не
стоит экономить: индексные сканы витрины упираются в задержку диска, и
разница между NVMe и SATA SSD здесь видна невооружённым глазом.

## Настройка PostgreSQL

Для 16 ГБ ОЗУ (подставьте свои, пропорции важнее чисел):

```conf
shared_buffers = 4GB              # ~25% ОЗУ
effective_cache_size = 12GB       # ~75%, подсказка планировщику
work_mem = 32MB                   # на операцию сортировки, не на сессию
maintenance_work_mem = 1GB        # ускоряет CREATE INDEX и VACUUM
random_page_cost = 1.1            # для SSD; дефолт 4.0 врёт про NVMe
effective_io_concurrency = 200    # NVMe умеет много параллельных чтений
max_connections = 100             # больше не нужно: пул в приложении
jit = off                         # на коротких запросах JIT только мешает
```

`random_page_cost = 1.1` — самая важная строка. С дефолтным `4.0`
планировщик считает случайное чтение вчетверо дороже последовательного и
выбирает seq scan там, где индекс быстрее.

**Про `max_connections`.** Держите его низким и пулите в приложении
(`DB_MAX_CONNS`). Правило: `DB_MAX_CONNS × число реплик API + запас на
worker и миграции < max_connections`. Постгресу дорого обслуживать сотни
соединений, а пул делает это бесплатно.

## Объектный сторидж и CDN

Видео **никогда** не отдаётся из API — только с CDN. Это не оптимизация, а
условие работоспособности: один поток 1080p съедает больше трафика, чем
тысяча запросов к витрине.

- Сторидж: **MinIO** на своём железе или любой облачный S3. Код работает с
  обоими, различие — в переменных окружения.
- Перед сториджем обязателен CDN, `MEDIA_CDN_BASE` указывает на него.
- Видео хранится как HLS-лесенка (480p/720p/1080p) плюс кадр-постер.
  Оригиналы не отдаются наружу никогда.

## Переменные окружения

Обязательные в проде:

```bash
APP_ENV=prod
DATABASE_URL=postgres://user:pass@host:5432/sk_store?sslmode=require
JWT_SECRET=<не меньше 32 байт из криптографического генератора>
REDIS_ADDR=host:6379
S3_ENDPOINT=... S3_BUCKET=... S3_ACCESS_KEY=... S3_SECRET_KEY=...
MEDIA_CDN_BASE=https://cdn.example.com
PUBLIC_BASE_URL=https://api.example.com
```

`JWT_SECRET` короче 32 байт в проде — приложение не стартует намеренно.
Полный список с дефолтами — `internal/config/config.go`.

## Порядок выката

```bash
go build -o api    ./cmd/api
go build -o worker ./cmd/worker
go build -o migrate ./cmd/migrate

./migrate          # отдельным шагом, до перезапуска API
systemctl restart sk-api sk-worker
```

Миграции — **отдельный шаг**, не на старте API: иначе реплики гонятся друг
с другом. Раннер берёт advisory-lock, так что параллельный запуск
безопасен, но сериализовать его явно всё равно правильнее. Файл миграции,
уже применённый и потом изменённый, раннер отвергает по контрольной сумме —
это защита от тихого расхождения схемы, а не придирка.

API умеет graceful shutdown: по SIGTERM дожидается текущих запросов
(`SHUTDOWN_TIMEOUT`, по умолчанию 20 с). Выкат без ошибок у пользователей.

## Резервные копии

Без этого запускаться нельзя:

- PostgreSQL: `pg_dump` ежедневно **плюс** WAL-архивация для
  восстановления на момент времени. Дамп раз в сутки означает потерю до
  суток.
- Проверяйте восстановление. Непроверенный бэкап — это не бэкап.
- Сторидж: версионирование бакета. Видео авторов не восстановить ничем.

## Наблюдаемость

Что есть в коде уже сейчас: структурные JSON-логи (`slog`), сквозной
`X-Request-ID`, `/healthz` и `/readyz`, access-лог со статусом и временем.

Чего нет и что стоит добавить при росте: метрики Prometheus, трассировка,
`pg_stat_statements` на стороне БД. Последнее включите сразу — это первое,
куда вы посмотрите, когда витрина начнёт тормозить.

## Где будет больно при росте

Честно, по порядку вероятности:

1. **Трафик на видео.** Самая дорогая позиция, растёт быстрее всех.
   Смягчается CDN и разумной лесенкой качества.
2. **«Могу приготовить сейчас».** Самый тяжёлый запрос витрины — 48 мс на
   50k рецептов (см. `PERFORMANCE.md`). Кэшируйте в Redis по хешу состава
   кладовой.
3. **Транскодирование.** Упирается в CPU. Лечится добавлением worker-ов:
   очередь на `FOR UPDATE SKIP LOCKED` рассчитана на несколько
   потребителей.
4. **Модерация.** Не техническая проблема, а людская: разбор жалоб не
   масштабируется добавлением железа. Закладывайте время людей.

## Чего в этой сборке ещё нет

Прямо и без прикрас: платежей нет, выплат авторам нет, нагрузочного теста
на конкурентных запросах не было, а ffmpeg в контейнере разработки
отсутствует — путь транскодирования собран и покрыт тестами на подменах,
но ни одно настоящее видео через него не проходило. Это надо прогнать на
вашем железе до первого реального пользователя.
