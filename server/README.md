# Бэкенд магазина рецептов

Сервис витрины и обмена рецептами для «Sasha's Kitchen». Go 1.24,
PostgreSQL 16, Redis, S3-совместимый сторидж.

> **Статус: в разработке, в продакшн не выкатывается.** Приложение к этому
> сервису намеренно не ходит: вкладка «Магазин рецептов» показывает
> «Скоро». Подключение — отдельным осознанным шагом, когда магазин будет
> достроен.

## Зачем отдельный сервис

Приложение полностью локальное: SwiftData на устройстве, без сети. Магазин
— это единственная часть, которой нужен сервер, и он живёт отдельно,
чтобы холодильник, рецепты и список покупок продолжали работать без
интернета и без аккаунта.

Формат обмена — обычный JSON поверх HTTPS, без Apple-специфики:
клиенты на Android и Windows запланированы и должны читать ровно то же.

## Запуск

```bash
export DATABASE_URL="postgres://sk:sk@127.0.0.1:5432/sk_store?sslmode=disable"
go run ./cmd/migrate     # схема
go run ./cmd/api         # API на :8080
go run ./cmd/worker      # фоновые задачи (транскодирование)
```

Все настройки — из окружения, с безопасными значениями по умолчанию для
разработки. Секреты значений по умолчанию не имеют: в проде без
`JWT_SECRET` сервис не стартует намеренно. См. `internal/config/config.go`.

## Тесты

```bash
export DATABASE_URL="postgres://sk:sk@127.0.0.1:5432/sk_store?sslmode=disable"
go test ./...
```

Тесты, которым нужна база, при отсутствии `DATABASE_URL` аккуратно
пропускаются, так что `go test ./...` работает и без PostgreSQL. Но
«пропущено» — это не «пройдено»: перед мержем прогоняйте с базой.

## Где что лежит

| Путь | Роль |
|---|---|
| `cmd/api` | HTTP-сервер витрины |
| `cmd/worker` | фоновые задачи: транскодирование медиа |
| `cmd/migrate` | миграции отдельным шагом деплоя |
| `migrations/` | схема, по одному файлу на изменение |
| `internal/search` | фильтры и поиск, keyset-пагинация, фасеты |
| `internal/storefront` | полки витрины и карточка рецепта |
| `internal/bundle` | самодостаточный payload для импорта в клиент |
| `internal/moderation` | публикация, жалобы, блокировки |
| `internal/auth` | аккаунты, токены, Sign in with Apple |
| `internal/media` | загрузка, транскодирование, HLS |
| `internal/author` | публичные страницы авторов, подписки |
| `internal/posts` | блог и короткие видео: типизированные блоки, лента |
| `internal/studio` | рабочее место автора: профиль, черновики, публикация, квоты |
| `internal/testdb` | отдельная база на каждый тестовый пакет |
| `internal/social` | жалобы и блокировки — то, чего требует Guideline 1.2 |
| `internal/jobs` | очередь фоновых задач на Postgres: реестр обработчиков, повторы, периодические задачи |
| `internal/paging` | keyset-курсор, общий для всех листингов |
| `internal/httpx` | ошибки, JSON, middleware |

## Инварианты, которые легко сломать

**Нормализация имени продукта должна совпадать в трёх местах:**
`sk_normalize_key()` в SQL, `search.NormalizeKey()` в Go и та же логика в
клиенте. Расхождение не вызывает ошибки — оно молча перестаёт
сопоставлять продукты рецепта с холодильником пользователя. За этим
следит тест `TestNormalizeKeyMatchesSQL`.

**Ингредиент несёт полное определение продукта, а не ссылку на общий
каталог.** Это то, что позволяет клиенту создать у себя продукт, которого
он никогда не видел, и заодно замораживает числа автора: правка
где-то ещё не должна задним числом переписывать опубликованный рецепт.

**Курсор сравнивает `(ключ_сортировки, id)` как строку.** Оба столбца
обязаны сортироваться в одну сторону, иначе сравнение перестаёт
соответствовать индексу. См. комментарий в `migrations/0002_recipes.sql`.

**Платный рецепт не отдаёт состав ни карточкой, ни bundle.** Проверка
владения живёт там, где отдаётся содержимое, а не только на входе.
